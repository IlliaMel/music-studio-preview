# Ordered remix sources

POST /v1/tracks accepts remixTrackIds, an ordered array of up to four distinct original IDs in mock mode. New clients should send the array only when nonempty. The legacy remixTrackId scalar remains accepted when the array field is absent, and normalizes to a one-element array. Supplying both fields, even an empty array, returns 400 VALIDATION. Duplicate IDs and arrays over four return 400; an uploaded reference together with remix originals returns 422 INVALID_REFERENCE. An empty array is ordinary prompt generation.

Responses return ordered remixTrackIds plus legacy remixTrackId as the first source or null. Migration 0007 backfills old scalar sources into the new array; reads and idempotency comparisons also fall back to the scalar for old rows. Array order is part of request identity. A legacy scalar request and its matching singleton array reuse the same Idempotency-Key and return the existing group without spending another credit. Reordering or changing sources with the same key returns 422 IDEMPOTENCY_KEY_REUSED. All variants persist the same source identity and the worker forwards every source after restart.

Each generated source must belong to the current owner, be visible, Ready and an Original. Every source is checked, not only the first. A missing/deleted/foreign source returns 404 TRACK_NOT_FOUND, a remix returns 409 REMIX_OF_REMIX, and unfinished originals return 409 NOT_READY. SQL repeats these checks under sorted source row locks before inserting the group or reserving quota, preventing deletion races. Public fictional catalog originals are allowed only in mock mode. Recording Drafts remain separate: use their bytes through the uploaded-reference contract, not recording IDs as remix originals.

GET /v1/capabilities reports maxRemixSources=4 for mock, 1 for the current live adapter and 0 when live references are disabled. remixOutput is fixture-no-audio-blending for mock and single-source-conditioning for live. Mock output is synthesized fixture audio: accepting multiple source IDs does not claim to blend or transform their audio. One group still uses one local daily generation credit even with two variants.

Live requests with more than one original are rejected as 422 UNSUPPORTED_MODE before queue insertion, quota reservation, reference access or paid HTTP. The adapter itself also fails closed. Single-source live remix still requires the owner's completed ElevenLabs original with a reusable stored song ID and references enabled on the server. Catalog mock sources are not silently uploaded or billed to enable live remix. Uncertain paid-request no-retry behavior remains unchanged.

A live remix is planned before it is composed. The free composition-plan endpoint receives the original's description and genres together with the requested change, and its sections supply the style tags, because a request such as "make it more rocky" is not a style by itself. A vocal remix without its own lyrics sings the original's words: the lines sung in the part of the original that fits the remix length, shared out across the planned sections. Only an original without words keeps the planned lyrics. The original conditions the first section at low strength, so that the requested change is audible. If planning fails, the remix still composes once, with the request as its style. Plan cues such as `{generate vocals}` and section labels are never returned as sung words.

The official v2/v2.5 schema permits one conditioning_ref per generation chunk and a composition plan containing multiple chunks. Distinct per-chunk song IDs are a plausible future ordered-section mapping, not a verified simultaneous blending contract. The current live adapter uses one source; maxRemixSources must not be increased until it consumes every source. Official sources:

AllowRemixes and LockLyrics policies, publishing and multi-source live generation are not implemented.
